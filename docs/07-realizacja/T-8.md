## Co zrobiono

- package.json (pnpm) ze skryptami lint, typecheck, test, build → `package.json`: `lint` = `eslint .`, `typecheck` = `tsc --noEmit`, `test` = `vitest run`, `build` = `tsc -p tsconfig.build.json`; `packageManager: pnpm@12.16.1`, wersje zależności przypięte dokładnie, `pnpm-lock.yaml` w repo.
- tsconfig.json w trybie strict, kod w src/, testy w tests/ → `tsconfig.json` (`strict`, dodatkowo `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, `NodeNext`), `include` obejmuje `src/`, `tests/` i `vitest.config.ts`; kod w `src/index.ts`.
- vitest skonfigurowany; test dymny `tests/smoke.test.ts` przechodzi → `vitest.config.ts` (`include: tests/**/*.test.ts`, środowisko node); test importuje `src/index.ts`, więc sprawdza też rozwiązywanie modułów.
- lint (eslint z typescript-eslint) i typecheck przechodzą → `eslint.config.js` (flat config: `@eslint/js` recommended + `typescript-eslint` `strictTypeChecked` z `projectService`, pliki `.js` bez reguł typowanych); `pnpm lint` i `pnpm typecheck` zielone.
- joby lint i test w `.github/workflows/ci.yml` uruchamiają `pnpm lint`, `pnpm typecheck` i `pnpm test` → job `lint`: install + lint + typecheck; job `test`: install + test + build. Akcje przypięte po SHA jak `actions/checkout`: `pnpm/action-setup` v6.1.1, `actions/setup-node` v7.1.0 (`node-version: lts/*`, cache pnpm). Pozostałe joby bez zmian.
- tabela stacku projektu w `AGENTS.md` uzupełniona → wiersze typ, framework, instalacja, lint, testy, build i uruchomienie lokalne.

## Decyzje

- Wersja TypeScript → 6.0.3, nie najnowsza 7.0.2, bo `typescript-eslint` 8.72.1 wymaga `typescript >=4.8.4 <6.1.0`; kryterium wymaga eslint z typescript-eslint.
- Pliki spoza „Zakresu” → dodane `src/index.ts` i `tsconfig.build.json`. Kryterium „kod w src/” wymaga choć jednego pliku w `src/` (inaczej `tsc` nie ma czego sprawdzać ani budować), a osobny `tsconfig.build.json` pozwala budować tylko `src/` do `dist/`, gdy `tsconfig.json` sprawdza typy także w `tests/`.
- Format modułów → ESM (`"type": "module"`, `NodeNext`), importy z rozszerzeniem `.js`; to obecny standard dla bibliotek Node.
- Wersja Node w CI → `lts/*` w `actions/setup-node`, zgodnie z kontraktem „Node LTS”; `engines.node >=24`. Brak `.node-version` dla fnm, bo plik jest poza zakresem.
- Instalacja pnpm w CI → `pnpm/action-setup` czyta wersję z pola `packageManager`, więc wersja pnpm jest w jednym miejscu.
- Poziom reguł lint → `strictTypeChecked`, bo szkielet jest pusty i łatwiej zacząć od ostrych reguł niż je później zaostrzać.
- Przeczytane źródła spoza „Wejścia” → `docs/konfiguracja.md`, `.github/PULL_REQUEST_TEMPLATE.md`, `.gitignore`, `docs/_szablony/raport-zadania.md`, `.claude/roles/worker/settings.json` (lista dozwolonych komend), API GitHub z tagami akcji (SHA do przypięcia). `docs/00-intake/specyfikacja.md` i `docs/04-architektura/architektura.md` nie istnieją w repo.

## Drobne uwagi

- Brak pliku `.node-version` / `.nvmrc` dla fnm; warto dodać w osobnym zadaniu, żeby lokalna wersja Node była przypięta.
- `README.md` nie opisuje jeszcze komend projektu (poza zakresem).

## Ryzyka

- CI na PR #14: `lint`, `test`, `gitleaks`, `check-dod` zielone; `testy-skryptow` czerwony w 2 testach `scripts/tests/sync-status.bats` („bez limity.md: pusta lista i bez zmian”, „pusta tabela decyzji: pusta lista”). Przyczyna poza tym PR: test kopiuje żywe `docs/` repo i zakłada pusty szablon `docs/decyzje.md` i świeży `docs/status.md`, a orkiestrator już wpisał tam dane projektu. PR nie zmienia `scripts/` ani plików wspólnych, więc nie naprawiam tego w zadaniu.
- Lokalnie testowane na Node 26 (bieżące LTS); `fnm` nie był dostępny w profilu workera, więc nie sprawdziłem przełączania wersji.
- `pnpm/action-setup` v6 deklaruje wsparcie pnpm do v12; przy przejściu na pnpm 13 trzeba będzie zmienić akcję (README wskazuje `pnpm/setup`).

## Propozycje dla systemu

- Profil workera nie pozwala na `fnm` ani `cat`/`head`; dodać `Bash(fnm list)` / `Bash(fnm current)`, żeby worker mógł sprawdzić wersję Node zgodnie z kontraktem „Node LTS przez fnm”.
- Szablon CI mógłby od razu zawierać przypięte SHA `pnpm/action-setup` i `actions/setup-node` (zakomentowane), bo worker nie ma `gh api` i musi szukać SHA przez WebFetch.
- `scripts/tests/sync-status.bats` powinien używać własnych fixture'ów `status.md` i `decyzje.md` zamiast kopii żywego `docs/`; po pierwszych wpisach orkiestratora job `testy-skryptow` jest czerwony na każdym PR projektu.
- Zadanie szkieletu powinno mieć w „Zakresie” `src/**` i `tsconfig.build.json` (albo ogólnie katalog kodu), skoro kryterium wymaga kodu w `src/`.
