# Raport T-51: QA M1: punkt wejścia pakietu nie eksportuje funkcji biblioteki

Issue: #51
PR: #52

## Co zrobiono

- `src/index.ts` reeksportuje sum, slugify, formatPLN i parseDate (`export { … } from './….js'`). Moduły
  funkcji są bez zmian, a `NAZWA` i `wersja` zostają eksportowane (używa ich `tests/smoke.test.ts`).
- Test `QA-M1-1` w `tests/qa/M1-przeplywy.test.ts` jest teraz zwykłym `test` zamiast `test.fails`.
  Przed zmianą `src/index.ts` był czerwony, po zmianie przechodzi.
- Po `pnpm build` polecenie `node --input-type=module -e "import * as m from 'sh-dryrun'; console.log(Object.keys(m))"`
  wypisuje `[ 'NAZWA', 'formatPLN', 'parseDate', 'slugify', 'sum', 'wersja' ]`, czyli zawiera wszystkie cztery funkcje.

## Testy

- `pnpm lint`: zielone
- `pnpm typecheck`: zielone
- `pnpm test` (komenda z issue): zielone, 6 plików, 69 testów
- `pnpm build`: zielone, a import `sh-dryrun` po buildzie jak wyżej
- `gitleaks git --redact --no-banner .`: brak wycieków

## Decyzje

- Czy usunąć `NAZWA` i `wersja` z punktu wejścia? → nie, bo issue tego nie wymaga, a usunięcie zepsułoby `tests/smoke.test.ts` i publiczne API.
- Czy kryterium „po pnpm build import zwraca cztery funkcje” sprawdzić testem automatycznym? → nie, sprawdzam je komendą z raportu. Test vitest wymagałby uruchomienia `pnpm build` przed testami, czyli zmiany skryptów albo CI spoza zakresu.

## Drobne uwagi

- brak

## Ryzyka

- Kryterium 3 (import zbudowanego pakietu) sprawdziłem ręcznie, a CI go nie sprawdza. Regresja w `package.json` `exports` albo w buildzie nie zostałaby wykryta testami.

## Propozycje dla systemu

- Szablon zadań typu biblioteka: dodać do CI krok smoke importu zbudowanego pakietu (`pnpm build` + `node -e "import … from '<nazwa>'"`), żeby kryteria dotyczące punktu wejścia miały test automatyczny.
